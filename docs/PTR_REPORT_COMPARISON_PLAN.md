# PTR 与 Report 核对方案

**版本**：方案草案 v0.3
**日期**：2026-10-24  
**原则**：规则先判定，LLM 只能辅助不确定部分；不能用 LLM 单独给出通过结论。

**当前进展（2026-10-24）**：已完成范围层、规则比较草案、OCR 观察适配器、矢量表格证据和 LLM 复核契约。`mvp/ptr_scope.py` 从 Report 第三页表格单元格提取并展开 `ScopeSet`，`mvp/ptr_compare.py` 已把有文字层 PTR 和 Report 产品技术要求拆成条款节点，输出带双方页码、坐标、原文和 SHA-256 的 Coverage Ledger；`mvp/ptr_ocr.py` 在本机 OCR 可用时为扫描 PTR 提供带置信度和 PDF 坐标的候选文字，仍强制进入 `manual`；`mvp/ptr_llm.py` 校验未来 LLM 返回的逐字证据，`apply_llm_review()` 只允许在数值、单位、引用和表格规则全部通过时消除文本人工项。`mvp/ptr_p01.py` 的禁用态草案已引用范围结构。条款解析现在对逗号、句点和无空格中文标题做有边界的内联拆分，并在 Report 侧保留序号身份；0775 的 `2.10.1.2.1`、`2.10.1.2.2`、`2.10.2.1`、`2.10.2.2` 已能在双方账本中一一对应，引用句不会被误识别成新条款。0596、1539、2795 已有黄金范围夹具和比较回归，5782 已验证无文字层时进入人工队列。PTR 能力仍保持禁用。

## 0. 当前已落地的比较草案

这一步先把“如何比”做成可运行、可复核的规则基线，不把它接入正式工作台的通过结论。

- 入口是 `mvp.ptr_compare.compare_ptr_report(report, ptr, comparison_mode="rules")`，也提供 `rules+llm` 入口；两种模式都先执行同一套规则，当前没有实际调用模型。
- PTR 先按 2.x 条款号和父子关系生成条款树；Report 先读取第三页 `检验项目` 得到范围，再从正式检验表读取 `检验项目/标准条款/标准要求`，把嵌在父条目中的子条款拆出来。
- 比较顺序是文本规范化、数值/单位/比较符、GB/YY 标准引用、表/附录引用和覆盖关系。空白、换行、全半角和 `ug/μg` 这类受控写法可以归一；数值、单位、上下限、引用缺失和条款缺失仍是硬差异。
- 每个条款都会进入 Coverage Ledger，状态只有 `matched`、`mismatch`、`manual`、`excluded`。规则无法确认时进入 `manual`，不会被当作一致；当前草案对明确范围外内容使用 `excluded`，不把未解析内容伪装成排除。表/附录引用另外保存 `bound`、`bound_physical_rows`、`ambiguous` 或 `unresolved` 绑定状态，未绑定不会被当作通过。
- `rules+llm` 只把规则识别出的文本歧义标记为待接入的 LLM 复核队列；表格结构、数值、单位、范围和引用硬差异不会送入可清除文本结论的队列。每个任务固定提示词版本和输入哈希，显式 provider 的返回会保存验证后的 JSON、模型信息和处理动作。输出固定 `publishable: false`，也不会改变 `report_ptr` 的禁用开关。
- 扫描 PTR 的 OCR 走本机已安装的 Apple Vision/RapidOCR 适配器；若没有引擎、引擎失败或候选条款不稳定，保存诊断、bbox 和置信度并保持 `manual`。OCR 只提供观察，不反向从 Report 补写 PTR。
- 能被 PyMuPDF 识别的矢量表格会作为物理行矩阵挂在条款节点上；双方矩阵规范化后完全相同才算表格一致，否则缺少结构证据时进入 `manual`。复杂无边框表格仍需人工标注和后续行列映射规则。
- PTR 和 Report 的条款正文按页面坐标重建；图注、页码和表格内容不会再按 PDF 对象顺序串入相邻条款。Report 合并的“标准要求”列按物理列边界完整读取，跨页续项仍保留原页证据。
- `mvp/ptr_llm.py` 已固定受约束 JSON：`decision`、缺少/增加概念、逐字引文、页码和原因。引文找不到、页码非法或格式错误都会拒绝回写；这一步没有任何模型供应商调用。

当前回归样本的预期用途如下：1539 固化 2.2.2 的表格人工复核、2.2.6 的单位归一后一致和 2.6 的文本/表格人工队列，2795 固化 2.5 的单位矛盾和 2.6.1 的表格人工复核，0596 固化深层条款树，5782 固化“无原生文字层必须人工复核”。这些是比较器的回归线索，不代表已经完成业务验收。

## 1. 看完素材后的结论

项目中的 PTR 比对目前还没有真正启用。`mvp/ptr_p01.py` 只生成候选条款、引用和父子关系，能力目录仍以 `PTR_NOT_VALIDATED` 禁用；它不能发布“相同”或“不同”的业务结论。

这不是把一个开关打开就能解决的问题，原因有四个：

1. PTR 有文字版，也有纯扫描版；同一份文件可能同时有正文、表格、附录和图片。
2. Report 的正文同时包含 GB 9706 等标准、产品技术要求和配套标准，不能把 Report 的全部文字与 PTR 全文直接比较。
3. Report 第三页的“检验项目”是一个范围声明，包含区间、单项条款、字母子项、“除外”和“仅检”，必须先展开范围再比较。
4. “格式不一样”与“内容不一样”要分开处理。换行、空格、全半角、单位写法可以等价；数值、单位、上下限、条件、对象或缺失内容不能被相似度掩盖。

因此建议把 PTR 比对做成一条固定流水线：

```text
原始 PDF（只读、留哈希）
  → 文本/表格/图片/OCR 提取
  → PTR 条款树 + Report 检验项目范围 + Report 条目表
  → 规则规范化和数值解析
  → 条款、表格、引用逐项比较
  → matched / mismatch / manual / not_applicable
  → 页码、坐标、双方原文和规则版本
```

LLM 只放在“规则无法确定”的几个插口中，且返回结果必须再次经过规则校验。

### 2.2 现有素材暴露出的实现问题

- 当前候选提取器按“看到数字开头的行就当条款”，会把页码、表格里的 `0`、`19`、`128` 等数值也当成条款。它适合做候选，不适合直接比较。

- Report 的同一条款可能拆成多个物理行，或一条 PTR 条款在 Report 中拆成父项和多个子项；必须保留层级和几何位置，不能只按序号顺序硬配。

## 3. 建议固定的比较对象

不要比较“整份 PDF”，而要比较下面四层对象：

### 3.1 范围层

从 Report 第三页的“检验项目”单元格提取并展开：

- `2.1～2.13` 这样的连续区间；
- `2.1.3～2.1.11` 这样的深层区间；
- `2.1.13b)`、`2.3.6.6a)～e)` 这样的字母子项；
- `除……` 排除项；
- `仅检……` 限定项和引用标准范围。

结果保存为 `ScopeSet`，每个选中或排除的条款都带第三页的原文和坐标。范围无法解析时，不猜范围，整项进入 `manual` 或阻断运行。

### 3.2 PTR 条款层

PTR 解析为 `RequirementGraph`，每个节点至少包含：

- 条款号、父条款号、标题和正文；
- 表格、图、附录和引用标准的引用关系；
- 适用条件，例如“仅适用于……”“当……时”；
- 数值事实：数值、单位、比较符、区间、允差、精度和取值方式；
- PTR 页码、bbox、原文和提取方式（原生文字或 OCR）。

表格不能只保存为一段文字，要保存表头、行键、列键和单元格坐标。

### 3.3 Report 条目层

Report 正式检验表解析为 `ReportItem`，至少包含：

- Report 序号、检验项目、标准条款；
- 标准要求的多级单元格和跨页续项；
- 检验结果、单项结论、备注；
- 条款号和项目的物理页、表格单元格 bbox。

Report 中属于 GB 9706.1、GB 9706.202、YY 标准的行不直接拿来与 PTR 条款比对；只有条款号/项目能落入 `ScopeSet` 的产品技术要求条目进入 PTR 比较。一个 Report 项目对应多个 PTR 子节点时建立一对多映射，并保留父项关系。

### 3.4 比较单元层

每一条比较单元固定保存：

```text
ptr_node_id
report_item_ids
scope_decision
title_comparison
text_comparison
numeric_comparison
table_comparison
reference_comparison
decision
reason_code
双方 evidence
```

这样既能显示“这一项是否一致”，也能回答“具体比较了哪一页、哪一个单元格”。

## 4. 规则独立模式（不调用 LLM）

规则独立模式应是默认基线，离线也能运行。建议按以下顺序执行。

### 第一步：输入和模板门禁

1. 检查两个 PDF 能打开、未加密、页数和页几何可读。
2. 运行前后保存并核对 SHA-256，原文件只读。
3. 校验 Report 编号、产品名称、技术要求标题的基本身份关系；身份不确定时不继续自动比对。
4. 记录模板指纹：页尺寸、Report 表头、PTR 是否有文字层、OCR 是否成功。未知模板不强行套用已知规则。

### 第二步：确定性提取

- 有文字层的 PTR：先用文本块和字符坐标，再用表格几何重建行列。
- 无文字层的 PTR：按页渲染 OCR；保留 OCR 文字、置信度和 bbox。OCR 只产生观察，不直接产生通过结论。
- Report：按表格单元格几何读取，不能只按 `get_text()` 的阅读顺序拼接。
- 图片、图注、附录需要参与要求内容时，记录为图像对象；无法读出时进入 `manual`。

### 第三步：确定性规范化

只消除排版差异，不改变技术意义：

- Unicode NFKC、全半角、空白、换行、项目符号、引号和括号统一；
- `YY 9706.102-2021` 与 `YY9706.102-2021` 统一为同一标准编号；
- `μg`、`ug` 等单位写法按受控单位词典归一，保留双方原文；
- `0.038"`、`0.038''` 等受控符号按单位词典处理；
- 中文标题前后多出的“1.”、“表头”只在确定是同一层级的版式包装时移除；
- 不把近义词、数值、单位、比较符、适用条件和对象名称随意替换。

### 第四步：逐项规则比较

建议在现有 `PTR-P01` 下拆成以下子规则（是否拆成独立规则 ID，待验收时冻结）：

| 子规则 | 核对内容 | 自动通过条件 |
| --- | --- | --- |
| P01-SCOPE | Report 声明范围、排除和仅检范围 | 范围可解析，所有选项有唯一条款证据 |
| P01-STRUCTURE | PTR 条款树与 Report 条款树 | 条款号、父子层级、一对多关系无歧义 |
| P01-TITLE | 条款号和标题 | 条款号一致；标题规范化后相同或有冻结的受控别名 |
| P01-TEXT | 标准要求正文 | 规范化文本逐句/逐项一致，未发现缺句或多句 |
| P01-NUMERIC | 数值、单位、比较符、区间、允差、精度 | 解析为同一数值事实；单位换算后相等 |
| P01-TABLE | 表头、行键、列键、单元格 | 结构和每个受控单元格一致；缺表或少行不能通过 |
| P01-REFERENCE | 表、附录、GB/YY 标准引用 | 引用目标存在，编号和范围一致，未形成循环 |
| P01-COVERAGE | 缺项、额外项、范围外项 | 任何未覆盖对象都有明确 `mismatch/manual/excluded` 处置 |
| P01-EVIDENCE | 证据和可追溯性 | 双方原文、页码、bbox、哈希和规则版本齐全 |

### 第五步：规则判定口径

- `matched`：条款、文本、数字、表格和引用均有充分证据且一致。
- `mismatch`：明确发现缺失、增加、数值/单位/条件/对象不一致，或范围内条款没有对应 Report 条目。
- `manual`：OCR、表格归属、父子关系、标题语义或引用展开无法唯一确定。`manual` 不是通过。
- `excluded`：经范围确认主动排除的内容，例如第一阶段暂不展开的外部表 3；不能把未识别内容伪装成排除。后续若要区分“明确不适用”和“范围外”，再增加独立的 `not_applicable` 状态。

规则模式的优点是结果可重复、可审计、可离线运行；缺点是遇到同义改写、复杂表格或扫描质量差时会产生较多 `manual`，这比误报“相同”安全。

## 5. 规则 + LLM 模式（可选增强）

此模式先完整执行规则。只有规则给出 `manual` 或“候选不一致但无法确定”时，才把最小证据片段交给 LLM。LLM 不读取整份 391 页 Report，也不直接决定最终状态。

### 5.1 适合交给 LLM 的位置

1. **OCR 文字校正**：对 5780、5782 或低置信度局部图像给出候选文字；候选必须能在图像或原 OCR 中定位，不能凭空补字。
2. **条款分段和父子归属**：当标题、表格和正文被扫描版式打散时，提出“这一段属于哪个条款”的候选；规则再检查条款号顺序、页内坐标和父子关系。
3. **非数值文本等价判断**：例如“符合 YY 9706.102-2021 及 GB 9706.202-2021 第 202 条的要求”和换行后的同一表述。LLM 只判断缺失/增加的概念，不得修改数字事实。
4. **表格行列映射**：扫描表格表头不清或 Report 把一行拆成多行时，LLM 提出行键/列键映射；规则检查行列数量和每个单元格值。
5. **复杂范围语言解释**：LLM 可以把“仅检某标准中的某几项”改写成显式条款集合，但集合必须由规则重新解析并与原文 token 对齐。

### 5.2 LLM 输出必须是受约束 JSON

建议固定为类似结构：

```json
{
  "decision": "equivalent|different|uncertain",
  "missing_concepts": [],
  "extra_concepts": [],
  "text_evidence": [
    {"side": "ptr|report", "quote": "必须能在原文中找到的短引文", "page": 1}
  ],
  "numeric_claims": [],
  "reason": "排版差异/语义缺项/无法判断"
}
```

程序必须逐项验证：

- `quote` 在对应 PDF 的原文/OCR 结果中确实存在，且能回到 bbox；
- 条款号、表格行列、数字、单位、比较符和范围集合没有被 LLM 改写；
- LLM 没有引用 Report 结果去反推 PTR 原文；
- 输出符合 JSON Schema，模型超时、格式错误、引用找不到时立即回到 `manual`。

### 5.3 LLM 不允许做的事

- 不能覆盖规则解析出的数值、单位、上下限、允差或极性差异；
- 不能因为“整体很像”而忽略缺少一行、一列、一个条件或一个适用对象；
- 不能把 OCR 猜测直接当作原文；
- 不能把 `manual` 自动改成 `matched`，除非双方引用已被程序校验且所有硬规则已通过；
- 不能因模型输出一句“相同”就改变 Coverage Ledger 或总体状态。

因此，LLM 的作用是减少人工阅读量，不是替代规则。LLM 关闭、不可用或供应商更换时，规则模式仍必须给出同样的硬差异和同样的证据。

## 6. 推荐的落地顺序

### 阶段 A：先冻结规则基线

1. 以 2948、0775、1539 作为第一批人工标注集，覆盖短 PTR、长 Report、表格和已知差异。
2. 以 2795、3940、5780、5782 的历史期望 JSON 作为回归线索，但先人工确认哪些是格式误报、哪些是真差异。
3. 冻结 `ScopeSet`、`RequirementGraph`、`ReportItem`、`ComparisonUnit` 和 Coverage Ledger schema。

### 阶段 B：规则独立实现

1. 先完成 Report 第三页范围的几何提取和范围展开。
2. 继续用人工标注冻结 PTR 条款树中的标题、父子边和重复表头，避免把当前确定性树的剩余歧义当作事实。
3. Report 物理单元格证据和矢量表格矩阵已接入；1539 第 159 项表 6 的跨页续行、合并组件列和功能列已按物理列重建，并与 PTR 表 6 做语义矩阵比较；波形表等仍无法唯一映射的表格继续进入 `manual`。
4. 完成文本规范化、数值 AST、单位换算、表格比较和引用展开。
5. 先在 10 组有文字层 PTR 上闭合，再处理 5780、5782 的 OCR PTR。

### 阶段 C：可选 LLM 接口

1. 只接收规则筛出的最小证据片段；按输入哈希、提示词版本和模型缓存。
2. `mvp/ptr_llm.py` 已固定“语义等价/缺项解释”的 JSON 验证、提示词版本和输入哈希；`run_llm_reviews()` 已保存显式 provider 的验证输出审计记录。接入实际供应商仍需先确定供应商和本地密钥存储方式。
3. 记录供应商、模型、提示词版本、输入哈希、输出 JSON、验证结果和人工复核动作。
4. LLM 开关关闭时不改变规则硬判定；当前 `apply_llm_review()` 只允许减少部分文本 `manual`，不能改变已确认的数值、单位、范围或引用差异。

### 阶段 D：启用门槛

只有同时满足以下条件，才把 `report_ptr` 从 `disabled` 改成 `enabled`：

- 至少 3 份结构明显不同的 PTR（建议 2948、0775、1539）完成逐条人工对照；
- 范围内缺项、范围外条款、父子条款、表格、引用和循环引用都有正反测试；
- 规则模式和规则+LLM 模式的硬差异一致，LLM 不能制造“自动通过”；
- 每个纳入对象都有 Coverage Ledger，`eligible == accounted` 且有双方证据；
- 规则、解析器、单位词典、提示词、模型和结果 schema 都有版本号；
- 全流程通过 preflight、worker、publish 和双 PDF 定位回归。

在此之前，PTR 可以生成“解析草案/人工复核队列”，但不能生成空通过或对外宣称已经完成 PTR 自动核对。

## 7. 最终建议

现在最合适的实施选择是：**先做规则独立版，规则+LLM 作为第二个可选开关**。先把“范围、条款、表格、数值和证据”这五件事做成稳定的机器事实，再让 LLM 处理少量语言歧义。这样即使 LLM 关闭，工具仍能完成硬规则核对；开启 LLM 时，人工只需查看规则无法判定的少数条目。
